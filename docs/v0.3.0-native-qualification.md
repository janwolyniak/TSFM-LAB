# Native Windows qualification worksheet

Prepared 2 November 2026 from the current v0.3.0 implementation. **No native
check is marked passed by this worksheet.** The published release's existing
limits remain in [release verification](v0.3.0-verification.md); acceptance is
defined by [S8/S9](release-v0.3.0-plan.md#s8-native-windows-compatibility).

## What each host can establish

| Check | Hosted Windows runner | Windows 11 + Windows Terminal |
| --- | --- | --- |
| Native source tests, Black/Ruff, build, wheel installation and redirected CLI | Executable by the existing workflow, on its recorded Server image | Repeat for the advertised desktop target |
| Baseline onboarding/preferences, historical/future workers, comparison and exports | Installed verifier exercises these through disposable programmatic input | Also inspect the actual keyboard-driven journey |
| Drive paths, Unicode/spaces, ordinary locking and filesystem publication | Native tests execute on the runner's local disk | Repeat on the selected local NTFS drive |
| Private-console Ctrl+C and worker reaping | Executable if the runner exposes an attachable private console; a skip is not a pass | Repeat; additionally send Ctrl+C from Windows Terminal |
| Completion, arrow history, back/cancel, visible progress and native scrollback | Headless UI tests do not establish keyboard/ConPTY behavior | Requires the actual Windows Terminal/PowerShell session |
| Real optional runtime imports and CPU inference | Technically executable with separately provisioned runtimes/weights; absent from current CI | Requires the same explicit family-specific setup |
| Windows Credential Manager and browser sign-in | A disposable Server/service account cannot certify the user's desktop session | Requires an interactive user session and authorized account actions |

The workflow's `windows-latest` label is not an exact OS identity. Retain the
actual runner-image version and Windows build from each executed job. Neither
macOS tests nor simulated Windows path/MSVCRT fixtures establish native success.

## Evidence required for every executed case

Record case ID, date/operator, outcome (`passed`, `failed`, `skipped` or
`not run`), exact command/action, expected/observed behavior, duration and report
location. Include source revision, package version, wheel SHA-256, Python
version/architecture, Windows edition/build, PowerShell version, Windows Terminal
version and filesystem. A source test and a separately installed release wheel
must retain their own identities if they differ. Preserve failed attempts and
specific skip reasons; do not convert an unavailable prerequisite into a pass.

Capture nonsecret host details in PowerShell:

```powershell
Get-CimInstance Win32_OperatingSystem | Select-Object Caption, Version, BuildNumber, OSArchitecture
$PSVersionTable.PSVersion.ToString()
Get-AppxPackage Microsoft.WindowsTerminal | Select-Object Name, Version
py -0p
```

If Windows Terminal is not installed through Appx, record the version shown in
its About screen. Retain package versions, `pip check`, model file hashes and
resource measurements for model cases. Never put keys, tokens, browser callback
URLs, account identifiers or private datasets into retained/public evidence.

## Native core and interactive checklist

Use an authorized disposable local directory and existing/approved dependencies.
Freeze the candidate source and exact wheel first; follow the
[Windows setup](windows.md#candidate-powershell-setup) and
[ordinary installed verification](releasing.md#verify-an-ordinary-installation-outside-the-checkout).
Repeat the core cases on x64 Python 3.11, 3.12 and 3.13. TOTO execution is excluded
on 3.11; detached record viewing must still work there.

```powershell
$tsfmQualificationRoot = Join-Path $env:TEMP ('TSFM qualification Łódź ' + [guid]::NewGuid().ToString())
New-Item -ItemType Directory -Path $tsfmQualificationRoot | Out-Null
$env:TSFM_LAB_SETTINGS_DIR = Join-Path $tsfmQualificationRoot 'preferences'
$env:PYTHONUTF8 = '1'
$env:OPENBLAS_NUM_THREADS = '1'
$env:OMP_NUM_THREADS = '1'
$env:MKL_NUM_THREADS = '1'
```

These are process-local test settings. `TSFM_LAB_SETTINGS_DIR` isolates
preferences, **not** connection metadata or the native credential vault. Use
explicit disposable connection state for noninteractive probes, and only
purpose-labeled test profiles/references for authorized native menu/vault checks.

1. **W1 — install and baseline acceptance.** Install the exact wheel with
   CLI/Parquet dependencies into a fresh environment without system site
   packages. Record `pip check`, `tsfm --version`, module/executable paths and
   `Get-FileHash -Algorithm SHA256` for the wheel. Outside the source checkout,
   put that environment's `Scripts` directory first on PATH and execute
   `python -I <source>\scripts\verify_distribution.py --wheel <exact-wheel>`.
   Retain its JSON and exit status; all 15 workflow stages must execute.
2. **W2 — native source suite.** Use a source-test environment with the approved
   `dev,cli,parquet,tui,connections` extras, as in the existing workflow. From the frozen source, run
   `python -m pytest -ra --junitxml=<evidence>\native-tests.xml`, Black and Ruff
   using the repository's configured targets. Run the existing
   `tests/test_portable_paths.py` native drive case and
   `tests/test_windows_console.py` private-console case. Retain actual skip
   reasons, including unavailable console attachment and symlink privilege 1314.
3. **W3 — first launch.** In Windows Terminal run `tsfm ui --workspace
   '<disposable results path>'`. Check setup, skip, cancellation without partial
   preferences, restart, `/setup` and `/settings`. Use spaces and `Łódź` in local
   paths. Verify persisted choices, explicit workspace precedence, and no movement
   or overwrite of existing results when changing defaults.
4. **W4 — keyboard and navigation.** Use Tab completion, arrow history,
   `/new guided`, `/back` and `/cancel` at model, data, mode and confirmation
   steps. Select each usage category, inspect original-unit Unicode output,
   scroll back after progress, resize the terminal, and return to the prompt.
   Check both historical and future mode; future accuracy must be unavailable.
5. **W5 — saved results.** Run `/demo` and guided historical/future baselines.
   Check the displayed CSV/JSON/chart/provenance paths, `/history`, `/show`,
   eligible historical comparison and CSV/JSON/Parquet export. Copy records into
   another test directory, make their input sources unavailable and reload/export
   without model packages. Future comparison/finance must refuse the record.
6. **W6 — cancellation and failure.** Press actual Ctrl+C during preparation and
   running; repeat during an explicitly authorized real model run. Check return
   to prompt, the terminal preparation/run status and unchanged completed records.
   Use the automated forced-stop/failure tests for deterministic escalation cases;
   confirm their task-owned worker PIDs have exited. An already atomically
   completed run may truthfully remain completed after a late cancellation.
7. **W7 — filesystem boundaries.** Check absolute/relative drive paths, quoted
   backslashes, Unicode/spaces, unavailable drive rejection and export overwrite
   refusal. Exercise an exclusive handle on a task-owned output file and two
   processes contending for the same task-owned connection lock. Verify bounded
   failure/retry, lock release after an exception, atomic records and preservation
   of existing bytes. UNC/device/drive-relative paths remain unsupported.
8. **W8 — native connections.** With fake provider transports, check route/menu
   selection, replacement, cancellation and secret redaction. Separately test the
   actual Windows vault with a synthetic sentinel under a fresh UUID: store,
   retrieve after process restart, delete only that UUID, and verify absence.
   Exercise explicit session-only storage and vault-unavailable errors without
   plaintext fallback. Record the actual backend; an injected fake backend does
   not qualify Credential Manager. Authorized browser sign-in needs its own
   user-present test of completion/cancellation/disconnect. Live provider requests
   retain their separate credential, consent and usage scope.

## Optional family qualification

For every advertised `(Windows build, Python minor, family)` tuple, retain an
actual clean installation/import result, resolved dependency versions and
`pip check`; then exercise a bounded CPU forecast and verified cached repeat.
Use separate disposable family environments where their constraints differ;
do not infer simultaneous installability from individually compatible pins.
The current routine CI installs no forecasting extra or checkpoint weights.
In the table, invoke pytest through the selected family's environment interpreter
(`Scripts\python.exe -m pytest`), not an unrelated executable found on PATH.

| Family | Maintained constraints / executable existing smoke | Additional evidence needed |
| --- | --- | --- |
| Chronos-Bolt | `requirements-chronos.txt`; `TSFM_CHRONOS_CHECKPOINT`, `pytest -m chronos_smoke` | Native strict load, finite aligned median output, cached repeat and saved outputs; preserve larger-variant status separately |
| Chronos-2 | `requirements-chronos.txt`; `TSFM_CHRONOS2_CHECKPOINT` or exact cache/revision, `pytest -m chronos2_smoke` | Native load, repeat/causality and saved historical/future output; Small evidence does not certify Standard |
| TimesFM 2.5 | `requirements-timesfm.txt`; `TSFM_TIMESFM_CHECKPOINT` or exact revision/cache, `pytest -m timesfm_smoke` | Native CPU float32 imports/loading, repeat, causal inputs and saved outputs |
| TiRex-2 | `requirements-tirex2.txt`; `TSFM_TIREX2_CHECKPOINT` or exact cache/revision, `pytest -m tirex2_smoke` | Native FlashRNN/Triton imports and eager CPU execution without compilation; record `triton-windows` version and preserve training-profile verification separately |
| TTM R2/R2.1 | `requirements-ttm.txt`; `TSFM_TTM_CHECKPOINT`, `pytest -m ttm_smoke` | Existing smoke is hourly with a four-step output; extend/use a real harness for daily 90/30, weekly 52/16 and new R2 512/192, 512/336, 512/720 full native horizons |
| TOTO 2 4M | `requirements-toto2.txt`; Python 3.12/3.13 only | No opt-in real smoke exists yet. Add/use a real-runtime harness for strict load, causal scaling/inverse, median output, replay, bounds, nonfinite refusal and persisted historical/future output |

The existing smoke tests consume already authorized local/cached weights and
never authorize downloads. Use the model guides for exact environment variables
and pinned revisions. Real acquisition must also qualify the guided missing-file
consent path, metadata/file identity, download/cache replay, interruption and
recovery; offline cache smoke alone cannot establish those steps. Retain resource
use and a bounded timeout for each family instead of starting a benchmark.

The [TTM record](s6-ttm-verification.md) identifies all five new profile revisions
and frequency-token contracts. Daily and weekly inputs require exactly one and
seven fixed UTC days, with native frequency tokens 8 and 9. Do not resample an
hourly smoke fixture and call it weekly/daily native evidence. TTM output is
`native_point`; TOTO output is `median`. The [TOTO record](s6-toto2-verification.md)
retains the precise runtime/checkpoint identity and project bounds. Running one
checkpoint establishes neither another checkpoint's real-inference status nor
forecast quality, throughput, memory requirements or trading value.

## Evidence gaps in the current automation

- `tests/test_native_lock_contention.py` now launches two independent isolated
  Python processes using the actual `StateStore.locked` API. It checks exclusive
  critical sections, retry after release, the real five-second contention
  timeout, recovery in the same contender process, generation ordering and an
  empty lock file without initialization writes. It uses MSVCRT on Windows and
  flock on POSIX, with bounded synchronization and cleanup. On 2 November 2026,
  the macOS 27.0.1 ARM64 / Python 3.13.6 counterpart passed both cases in 5.62 s;
  Black/Ruff passed. Both genuine MSVCRT cases also passed on Windows Server
  2025 Datacenter, reported OS version 10.0.26100, Python 3.12.10 x64, runner
  image `windows-2025-vs2026` version `20261030.294.1`, in the
  [focused native probe](https://github.com/janwolyniak/TSFM-LAB/actions/runs/41502684141/job/125473924276).
  This qualifies the exercised lock behavior on that tuple, not Windows 11 or
  other Python minors. `tests/test_windows_boundaries.py` retains its separate
  simulated failure-boundary checks.
- Private-console test skips with attach errors 5/6 are valid unavailable-host
  outcomes, not evidence for Windows Terminal Ctrl+C. Preserve both results.
- The CI workflow currently retains neither JUnit nor uploaded artifacts.
  `check_installed_distribution.py` writes exact build/verifier JSON under
  `RUNNER_TEMP`, but the VM is ephemeral. Retain JUnit and those reports/binaries
  through an artifact upload, alongside job URL, runner image and source SHA.
- Current model tests do not make the absent TOTO real smoke or the hourly TTM
  smoke representative of all added profile behavior. Native runtime jobs need
  explicit runtime/weight provisioning and distinct evidence for each behavior.
- The Windows setup guide still describes development source as newer than
  v0.2.0 artifacts. When retaining new evidence, reference the actual v0.3.0
  wheel/candidate identity and update that setup wording separately.

The same focused Windows probe passed the two real binary worker-pipe tests
(startup bytes, event framing, cancellation and ordinary pipe EOF), but the
full baseline application-startup probe timed out. Its aggregate result was
14 passed, 1 failed and 1 skipped. This is failed core qualification with useful
partial evidence; it does not establish working Windows baseline execution.
The first diagnostic dictionary was abbreviated by pytest, so its child stack
was not visible. The
[second focused trace](https://github.com/janwolyniak/TSFM-LAB/actions/runs/41503527494/job/125476835313)
showed the main thread waiting in NumPy's native module loading during
configuration unpickling, while the cancellation thread blocked in the private
pipe's CRT read. A Windows-specific watcher now polls `PeekNamedPipe` before
reading its control byte, and stops after execution, leaving the POSIX read
path and clean startup environment unchanged. The local clean-worker/execution/
portability selection passed 41 cases in 8.28 s; Black/Ruff passed. Native
verification of that repair remains pending until the changed code executes.

Close an original acceptance item only when all of its required observations
are retained. Hosted Windows Server success can advance the automated evidence;
Windows 11/Terminal, native user-session credentials and real models remain
separate until actually executed. Unsupported tuples require an explicit support
decision and honest labels rather than an automatic WSL substitution.
